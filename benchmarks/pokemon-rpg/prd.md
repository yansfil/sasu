# PRD: pokemon-rpg

## 1. Summary

저장소 루트의 `pokemon-rpg/`에 설치와 빌드 없이 플레이할 수 있는 완결된 2D 브라우저 RPG를 만든다.
플레이어블 주인공 5명, 맵 7장, 몬스터 20종, 단일 타입 7종, 야생전과 트레이너전, 포획과 성장, NPC 미션, 라이벌 최종전과 엔딩을 포함한다.
런타임 npm 의존성과 외부 에셋은 없고, 정적 모듈과 인라인 SVG로 동작한다.

이 PRD는 동시에 sasu 하네스의 표준 벤치마크 워크로드다.
제품 계약은 사용자가 관찰할 행동, 고정 규칙, 검증 의도만 소유한다.
파일 배치, 모듈 분할, 테스트 러너 경로, 패키지 스크립트, 실행 명령은 저장소를 읽은 구현 계획이 바인딩한다.
구현 계획이 다른 구조나 명령을 선택해도 이 문서의 의미 계약과 증거 강도를 그대로 만족하면 PRD 편차가 아니다.

Approval checklist:

- 스코프와 non-goal - §3
- 제품이 요구하는 경계와 제약 - §5
- 고정 콘텐츠 데이터와 게임 규칙 - §6
- task dependency는 PRD가 소유하고 구현 파일과 명령은 실행 계획이 소유하는 계약 - §8, §9
- required-for-done 검증 모드와 고유 실패 책임 - §9
- 스코프 축소 금지와 실패 공개 원칙 - §11

## 2. Problem, Goal, And Users

**Problem.**
사용자는 sasu 하네스를 반복해서 시험할 고정 워크로드가 필요하다.
기존 게임 벤치마크는 상태 교차가 얕아 하네스 변경이 실제로 복잡한 작업과 거짓 PASS를 더 잘 처리하는지 판별하기 어렵다(D-01).
동시에 PRD가 아직 존재하지 않는 파일 구조와 검증 명령까지 미리 정하면, 제품 결정과 구현 판단이 섞이고 judge가 봐야 할 변경 범위를 누락시킬 수 있다.

**Goal.**
브라우저에서 시작부터 엔딩까지 완주 가능한 게임을 제공한다.
전투, 포획, 성장, 미션, 영속 규칙은 확률까지 결정적으로 재현 가능해야 한다.
각 acceptance criterion은 그 의미에 맞는 가장 강한 증거로 독립 판정할 수 있어야 한다.
검증 체계는 구현보다 무거운 두 번째 구현이 되지 않아야 한다.

**Users.**

- 데스크톱 브라우저와 키보드로 게임을 플레이하는 사람.
- 이 저장소에서 하네스를 개선하고 이 PRD로 구현과 검증 흐름을 관측하는 사람과 에이전트(D-05).

## 3. Scope And Non-Goals

### In Scope

- 타이틀, 주인공 선택, 이어하기, 확인 단계를 거치는 새로 시작.
- 계산에 반영되는 고유 특성을 가진 플레이어블 주인공 5명과 고정 시작 파트너.
- 서로 연결된 맵 7장과 메인 미션에 따른 순차 개방.
- 필드별 야생 인카운터와 안전한 전용 맵.
- 기술 4슬롯, PP, 타입 상성, STAB, 급소, 명중, 스피드 선공을 갖춘 턴제 전투.
- 도망과 포획이 가능한 야생전, 순차 파티와 보상이 있는 트레이너전.
- 파티 6마리, 몬스터볼과 상처약, 경험치, 레벨업, 진화, 기술 습득.
- 미션 NPC, 트레이너 NPC, 마을 NPC와 4종류·4단계 미션 시스템.
- 라이벌 최종전, 엔딩, 엔딩 후 계속 플레이, 도감 12종 달성 목표.
- 전멸 시 포켓몬센터 복귀와 전체 회복.
- 단일 로컬 세이브와 자동 저장.
- 디자인 토큰, 인라인 SVG, 키보드 접근성, 360px 반응형.
- 결정적 확률 제어, 규칙 회귀 검증, AC별 판정, 실제 브라우저 검증, 스크린샷 기반 시각 판정.

### Non-Goals

각 항목은 결과, 근거, 재검토 조건을 함께 적는다.

- **상태이상과 능력치 랭크 변화.**
  결과는 데미지, 명중, PP만 다루는 기술 체계다.
  지속 효과가 턴 파이프라인과 조합 검증을 크게 늘리므로 제외한다.
  전투 깊이를 더 요구할 때 재검토한다(D-33).
- **이중 타입.**
  모든 종은 단일 타입이다.
  상성 계산과 밸런싱 표면만 늘리고 새 규칙을 증명하지 않으므로 제외한다.
  로스터를 확장할 때 재검토한다(D-20).
- **3단계 진화.**
  진화 계열은 2단계다.
  동일한 진화 규칙의 반복이므로 제외한다.
  콘텐츠 확장 시 재검토한다(D-21).
- **난이도 선택 옵션.**
  난이도는 맵별 야생 레벨, 인카운터, 트레이너 파티 곡선으로 표현한다.
  별도 난이도 시스템을 원하지 않는 사용자 결정을 따른다(D-18).
- **상점과 돈.**
  아이템은 시작 지급, 1회성 타일, 미션 보상으로 얻는다.
  경제 시스템이 별도 밸런싱 표면을 만들기 때문에 제외한다(D-31).
- **온스크린 터치 조작.**
  360px에서 레이아웃은 유지하지만 키보드가 없으면 플레이할 수 없다.
  별도 입력 계층과 QA 레인이 필요하므로 제외한다.
  모바일 플레이 요구가 생기면 재검토한다(D-40).
- **사운드와 음악.**
  무음 플레이며 오디오 에셋과 자동재생 정책을 다루지 않는다.
- **멀티플레이, 통신 교환, 온라인 랭킹.**
  서버, 인증, 개인정보 경계를 만들지 않는 오프라인 1인 게임이다.
- **다중 세이브 슬롯과 세이브 내보내기·가져오기.**
  로컬 슬롯 하나만 제공한다.
- **번들러, 프레임워크, 런타임 npm 의존성, 외부 이미지·폰트·CDN 에셋, 생성형 이미지.**
  그대로 서빙하는 정적 앱과 직접 그린 SVG·CSS만 사용한다.
  정적 타입 검사와 자동 브라우저 검증을 위한 개발 도구는 이 제한의 예외다(D-07, D-09, D-11).
- **세션 분석 도구, 계측 코드, 벤치마크 리포트 생성기, 벤치마크 실행 스킬.**
  실행 후 분석과 벤치마크 자동화는 별도 작업이다(D-08, D-49).

추가 가정은 다음과 같다.

- A1. 앱의 제품 경계는 저장소 루트의 `pokemon-rpg/`다.
- A2. 딜리버리 모드는 `local`이며 커밋, 푸시, PR은 이 실행의 의무가 아니다.
- A3. 표 A부터 D의 구체 값은 인터뷰가 정한 수량과 구조 안에서 작성자가 구성했으므로 승인 대상이다.
- A4. 캐릭터 특성은 기계 판정 가능한 단일 수치 효과로 표현한다.

거부되거나 보류된 옵션은 난이도 선택, 캐릭터별 시작 맵, 미션 전용 잠금 맵, 생성형 이미지, 픽셀 인덱스 에셋, 스코프 축소, PRD 분할, 원샷 실행이다.

## 5. Major Technical Structure Changes

- 저장소 루트에 기존 harness와 런타임 의존 관계가 없는 자족적 정적 웹앱 경계를 추가한다.
- 고정 콘텐츠 정의, 결정 가능한 게임 규칙, 브라우저 입출력의 책임을 분리한다.
  구체 모듈 수와 파일 배치는 구현 계획이 선택하되, 규칙 검증이 DOM 조작을 요구하지 않는 경계는 보존한다.
- 모든 확률 의존 동작은 같은 시드와 입력으로 같은 결과를 내는 제어 가능한 무작위성 경계를 통과한다.
- 영속은 브라우저 localStorage의 단일 슬롯으로 제한한다.
  저장 형식은 버전 변화와 손상된 데이터에 안전하게 대응할 수 있어야 하지만 키 이름과 스키마 모듈은 구현 계획이 정한다.
- 자동 브라우저 검증은 실행 때마다 자체 앱 서버를 시작하고 종료하며 공유 브라우저 데몬에 의존하지 않는다.
- 각 machine-testable AC는 독립 실행 가능한 pass/fail 판정을 가져야 한다.
  그 인터페이스의 경로와 명령은 구현 계획의 verification binding에 기록한다.

### 6.2 Requirement List

- R1. **정적 웹앱 셸.** `pokemon-rpg/`를 로컬 정적 서버로 열면 설치나 빌드 없이 게임이 뜬다.
  런타임 npm 의존성, 번들러, 빌드 산출물, 외부 네트워크 요청, 콘솔 에러가 없다.
- R2. **플레이어블 캐릭터 5명.** 표 A의 5명이 고유 SVG, 이름, 특성 설명, 고정 시작 파트너와 함께 제시되며 그중 한 명을 선택한다.
  선택 캐릭터와 시작 파트너는 즉시 저장되고 별도 스타터 선택 화면은 없다.
- R3. **오버월드 이동.** 방향키와 WASD 4방향 이동, 충돌 차단, 플레이어를 따라가는 카메라를 제공한다.
  타일은 길, 풀숲, 장애물, 출입구, 1회성 아이템, 표지판, 회복의 의미를 가진다.
- R4. **맵 7장과 난이도.** 표 B의 필드 4장과 전용 3장을 제공한다.
  난이도는 레벨 구간, 인카운터, 트레이너 파티 강도로 표현하며 별도 선택 화면은 없다.
- R5. **미션 게이팅.** 출입구는 맵을 전환하고 잠긴 맵은 필요한 미션을 안내한다.
  개방 상태는 저장 후 복원된다.
- R6. **몬스터와 인카운터.** 표 C의 20종과 맵별 가중치 인카운터를 제공한다.
  뮤는 화산에서만 낮은 가중치로 출현하고 전용 맵에서는 인카운터가 없다.
- R7. **턴제 전투.** 표 D의 상성을 사용한다.
  데미지는 `((2 * Lv / 5 + 2) * 위력 * 공격 / 방어) / 50 + 2`에 STAB 1.5, 타입 상성, 급소 1.5(확률 1/16), 난수 0.85~1.00, 적용 가능한 캐릭터 배율을 곱한다.
  스피드로 행동 순서를 정하고 기술은 타입, 위력, 명중, PP를 가진 4슬롯이다.
  명중 실패도 PP를 소모하고, PP가 0인 기술은 선택할 수 없으며, 전부 0이면 대체 행동을 쓴다.
  포켓몬센터는 PP를 회복한다.
- R8. **전투 모드.** 야생전은 도망과 포획이 가능하다.
  트레이너전은 둘 다 불가능하고 상대가 2~3마리를 순차 투입하며, 승리 보상과 재대결 방지 플래그가 저장된다.
- R9. **포획.** `남은 HP 비율 x 종족 포획률 x 볼 보정 x 캐릭터 특성 배율`로 성공 확률을 계산한다.
  성공하면 파티와 도감을 갱신하고 실패하면 볼과 턴을 소모한다.
- R10. **파티 관리.** 파티는 최대 6마리며 가득 찬 상태에서는 볼 소모 없이 포획을 거부한다.
  순서 변경과 개체 상태 확인을 제공하고 전투 중 교체는 턴을 소모한다.
- R11. **아이템.** 몬스터볼 10개와 상처약 3개로 시작하되 민들레는 볼 20개로 시작한다.
  아이템 타일은 한 번만 획득할 수 있고 획득 상태가 저장되며 미션 보상으로도 아이템을 얻는다.
  상처약에는 적용 가능한 캐릭터 배율을 반영하고 센터는 파티의 HP와 PP를 전부 회복한다.
- R12. **성장과 진화.** 승리 경험치로 레벨업하고 스탯을 재계산한다.
  표 C의 레벨에 진화하며, 기술 4슬롯이 찬 상태의 새 기술은 건너뛰고 로그로 알린다.
- R13. **NPC와 미션.** 필드 맵마다 메인 미션 1개와 사이드 미션 3~4개를 둔다.
  특정 종 포획, 지정 트레이너 격파, 아이템 수집·전달, 야생 N마리 격파를 모두 사용한다.
  미션은 미수락, 진행중, 완료가능, 보상수령완료 순서로 전이하고 진행과 보상 상태가 저장된다.
  트레이너는 시야 감지로 전투를 시작하고 마을 NPC는 회복, 지급, 안내를 제공한다.
- R14. **퀘스트 로그.** 수락한 미션의 상태, 목표, 남은 진행량을 메뉴에서 확인한다.
- R15. **라이벌과 엔딩.** 메인 미션 4개 완료 후 보스방이 열린다.
  라이벌은 `지우 → 이슬이 → 웅 → 그린 → 민들레 → 지우` 순환에서 선택 캐릭터의 다음 인물이다.
  라이벌 파티 3마리는 그 인물의 시작 파트너 최종 진화형과 파이어를 포함한다.
  승리하면 엔딩을 저장하고 계속 플레이할 수 있지만 보스방에는 재입장할 수 없다.
- R16. **도감.** 조우와 포획을 구분해 기록하고 서로 다른 12종 포획 시 달성 표시를 켠다.
- R17. **세이브와 이어하기.** localStorage 단일 슬롯에 선택 캐릭터, 파티, 현재 위치, 인벤토리, 도감, 미션, 트레이너, 아이템 타일, 맵 개방, 엔딩 상태를 저장한다.
  이동, 전투 종료, 미션 상태 변화에 자동 저장하고 새로고침 후 이어간다.
  새로 시작은 확인을 거치며 취소하면 기존 세이브가 바뀌지 않는다.
- R18. **전멸 복구.** 전멸하면 진행 삭제 없이 마을 센터로 돌아가 전부 회복한다.
  선두가 기절하면 살아있는 개체로 교체한다.
- R19. **시각 완성도.** 타이포그래피, 컬러, 스페이싱, 라운드, 섀도의 디자인 토큰을 정의해 일관되게 사용한다.
  캐릭터, 몬스터, 타일, UI를 인라인 SVG와 CSS로 그리고 몬스터 20종은 색상 차이만이 아닌 형태로 구별한다.
- R20. **접근성.** 방향키·WASD 이동, Z·Enter 확인, X·Esc 취소·메뉴로 키보드만 사용해 완주할 수 있다.
  전투, 미션, 맵 결과를 텍스트와 `aria-live`로 알리고 포커스 링과 모션 감소 설정을 지원한다.
- R21. **반응형과 성능.** 360px에서 가로 스크롤이 없고 맵 전환과 전투 진입은 각각 500ms 이내다.
  오버월드 이동은 60fps를 목표로 하되 체감 부드러움은 사람 판단이다.
- R22. **결정적 확률.** 인카운터, 명중, 급소, 데미지 난수, 포획, 도망, AI 선택은 제어 가능한 동일 무작위성 경계를 사용한다.
  같은 시드와 입력은 같은 결과를 내고 제어되지 않은 별도 난수 호출은 없다.
- R23. **검증 인터페이스.** 정적 검사, 규칙 회귀, 각 machine-testable AC의 독립 판정, 실제 브라우저 완주, 주요 화면 캡처를 제공한다.
  판정은 반복 실행해도 워크스페이스를 바꾸지 않고 성공과 실패를 프로세스 밖에서 구분할 수 있어야 한다.
  정확한 명령, 러너 경로, 테스트 배치는 구현 계획에서 바인딩한다.

## 7. Acceptance Criteria

- AC1. 모든 소스 모듈이 구문·로드 오류 없이 해석되고 애플리케이션 진입이 실패하지 않는다.
- AC2. 시작 화면에서 표 A의 캐릭터 5명이 시작 파트너와 특성 설명과 함께 제시되고 전원 선택 가능하다.
- AC3. 같은 시드와 상황에서 지우의 인카운터 x1.20, 이슬이의 포획 x1.20, 웅의 회복 x1.30, 그린의 데미지 x1.10, 민들레의 시작 볼 20개가 실제 계산에 반영된다.
- AC4. 5명 각각을 선택했을 때 선택 캐릭터와 표 A의 시작 파트너가 정확히 저장된다.
- AC5. 로스터가 정확히 표 C의 20종이고 종, 타입, 분류, 진화 레벨, 출현 맵이 일치하며 모든 종이 단일 타입이다.
- AC6. 맵이 정확히 표 B의 7장이고 이름, 타입, 레벨 구간, 진입 조건과 필드 4장·전용 3장 구성이 일치한다.
- AC7. 전용 맵에서는 인카운터가 없고 필드에서는 해당 맵 표에 없는 종이 나오지 않으며 뮤는 화산에서만 나온다.
- AC8. 시작 직후 잠긴 출입구는 필요한 미션을 안내하고, 직전 메인 미션 완료 후 해당 전환을 허용한다.
- AC9. 맵 개방 상태가 저장과 복원 뒤에도 유지된다.

## 8. PRD-Level Tasks

이 task는 승인할 제품 capability를 묶는 단위다.
PRD가 capability 간 완료 의존성을 소유하며, 이 workload의 사용자 여정은 T1부터 T6까지 순차적으로 완성된다.
구현 계획은 소유자, 파일 write scope, task 내부 실행 단위만 정한다.
구현 계획은 필요하면 이 task를 더 작은 실행 단위로 분해할 수 있다.

- T1. 플레이 가능한 시작과 복원 흐름을 완성한다.
  정적 앱 진입, 캐릭터 선택, 시작 파트너, 기본 조작, 단일 세이브, 이어하기, 새로 시작을 사용자 관점에서 연결한다.
  Covers R1, R2, R3, R17, R20, AC1, AC2, AC3, AC4, AC25, AC27, AC28, AC31. Depends on: none.
- T2. 연결 월드와 단계적 개방을 완성한다.
  맵 7장, 충돌과 전환, 필드 인카운터, 미션 게이팅과 개방 영속을 연결한다.
  Covers R3, R4, R5, R6, AC5, AC6, AC7, AC8, AC9. Depends on: T1.
- T3. 전투에서 복구까지 한 사이클을 완성한다.
  결정적 전투, 야생전과 트레이너전, 포획, 파티, 아이템, 전멸 복구를 연결한다.
  Covers R7, R8, R9, R10, R11, R18, R22, AC10, AC11, AC12, AC13, AC14, AC15, AC16, AC26. Depends on: T2.
- T4. 성장과 미션 진행 사이클을 완성한다.
  성장과 진화, NPC, 4유형·4상태 미션, 보상, 퀘스트 로그, 저장 복원을 연결한다.
  Covers R12, R13, R14, AC17, AC18, AC19, AC23. Depends on: T3.
- T5. 최종전과 계속 플레이를 완성한다.
  라이벌 전파, 보스방, 엔딩, 엔딩 후 상태, 도감을 연결한다.
  Covers R15, R16, AC20, AC21, AC22. Depends on: T4.
- T6. 제품 품질과 증거 계약을 완성한다.
  시각 완성도, 접근성, 반응형, 성능, 정적 검사, 규칙 회귀, AC별 판정, 실제 브라우저 흐름, 스크린샷 판정을 연결한다.
  Covers R19, R20, R21, R22, R23, AC1, AC11, AC24, AC25, AC27, AC28, AC29, AC30, AC31. Depends on: T5.

## 9. Verification Contract

### 9.1 Test Mode Contract

| Mode | Required For Done | Covers | Human Decision |
| --- | --- | --- | --- |
| build/static | yes | 소스 유효성, 모듈 로드, 런타임 의존성 0 | none |
| automated behavior | yes | 게임 규칙, 상태 전이, 결정적 확률, AC별 판정 | none |
| browser/runtime | yes | 실제 브라우저 완주, 영속, 접근성, 반응형, 전환 성능 | none |
| visual judgment | yes | 화면 완성도와 스프라이트 구별 가능성 | 최종 미적 취향 |

브라우저 실증은 DOM 대체물로 통과한 이전 거짓 PASS를 막기 위해 required-for-done이다(D-44).
검증 방식은 각각 아래 고유 실패를 잡을 때만 유지한다.
구현 계획은 verify 전에 각 V 항목에 정확한 명령, 환경, 산출물, side effect, safe probe를 바인딩해야 한다.
PRD에 없던 공유 파일이 관련 변경으로 발견되면 검증 범위를 축소하지 않는다.

각 V 행은 독립적으로 실행하거나 판정할 수 있는 고유 실패 책임을 가진다.
같은 명령, 증거, 차단 시점을 가진 검증 의도는 한 행으로 합치며 같은 테스트를 별도 V 행 때문에 다시 실행하지 않는다.

### 9.3 Human Verification

- HV1. 인카운터 빈도, 전투 템포, 맵별 난이도 곡선, 엔딩까지 걸리는 시간, 미션 동선, 60fps 체감이 재미있고 부드러운지 판단한다.
  자동 검증은 규칙 정확성과 전환 상한을 증명하지만 재미와 미적 취향은 증명하지 않는다.

터치 조작 제외, 팬 구현 전제, 고정 콘텐츠 값, 60fps의 자동 판정 제외는 구현 후 검수가 아니라 §4.2 승인과 §10 리스크에 속한다.

## 10. Risks And Open Decisions

- **R-1. 워크로드가 한 실행에서 완주되지 않을 수 있다.**
  이것은 의도된 측정 조건이다.
  스코프를 줄이지 않고 미완료 범위와 원인을 그대로 보고한다(D-42).
- **R-2. 시각 품질에는 자동 기대값이 없다.**
  V4가 구조적 결함을 막고 최종 취향은 HV1이 판단한다(D-28).
- **R-3. 결정적 확률 경계가 깨지면 여러 규칙의 증거가 함께 무효가 된다.**
  AC3, AC7, AC11, AC13의 동일 입력 재현성이 이 경계를 드러내야 한다.
- **R-4. 콘텐츠 데이터 물량이 크다.**
  표 복사 오류를 AC5, AC6, AC10, AC17이 고정 계약과 직접 대조한다.
- **R-5. 원작 계열 명칭을 사용한다.**
  개인 학습·벤치마크용 비공개 팬 구현이며 에셋은 직접 그린다.
  공개나 배포 전에 재검토한다(D-13).
- **R-6. greenfield 검증의 실행 명령은 PRD 승인 시점에 아직 존재하지 않을 수 있다.**
  이 경우 verification plan은 `needs_binding`을 명시하되 구현 시작은 막지 않는다.
  최초 검증 실행이 실제 명령과 작업 디렉터리를 결속하며, 필수 V 항목이 끝까지 결속되지 않으면 완료를 명시적으로 막는다.
- **운영 조건.**
  verify FAIL은 override하지 않는다(D-46).
  사용자 승인 완료 후에만 구현한다(D-47).
  벤치마크 원본은 `agents/` 밖에 보관하고 실행마다 새 run으로 복사한다(D-48).
- **측정 한계.**
  이전 실행은 wall-clock 대부분이 단계에 귀속되지 않았다(D-43).
  단계 시간, 병목, 중복 판정은 실행 후 별도 분석하며 앱에 계측 기능을 추가하지 않는다(D-49, D-50).

## 11. Implementation Guardrails

- §6의 캐릭터, 맵, 몬스터, 타입, 미션, 검증 자산 수를 임의로 줄이지 않는다.
- 상태이상, 이중 타입, 3단계 진화, 상점·돈, 난이도 선택, 터치 조작, 사운드, 멀티플레이를 추가하지 않는다.
- 고정 데이터, 게임 규칙, 브라우저 입출력의 책임 경계와 제어 가능한 무작위성 경계를 보존한다.
  이 경계를 만족하는 구체 모듈 구조는 구현 계획이 선택한다.
- 런타임 npm 의존성, 번들러, 프레임워크, 외부 에셋, 생성형 이미지를 도입하지 않는다.
- 자동 브라우저 검증은 공유 chromux 데몬을 쓰지 않고 자체 프로세스를 시작하고 정리한다(D-07).
- 제품 변경은 `pokemon-rpg/` 경계 안에 둔다.
  `agents/`는 실행 기록만 소유하며 제품이나 검증 입력이 아니다.
- PRD의 `Covers`는 의미 추적 관계이지 judge diff를 줄이는 파일 allowlist가 아니다.
- 정확한 파일, 디렉터리, 명령, runner entry point는 구현 계획과 verification plan이 소유한다.
  의미 계약을 보존하는 변경은 PRD 편차가 아니다.
- 검증은 반복 실행해도 같은 코드와 입력에 같은 판정을 내고 워크스페이스를 변경하지 않는다.
- 실패와 blocked 상태를 pass로 표시하지 않는다.
- 세션 분석 도구, 계측 코드, 리포트 생성기, 벤치마크 실행 스킬을 만들지 않는다.

## 12. Implementation Result Report Contract

구현 결과는 다음을 보고한다.

- 상태를 `Done`, `Partially Done`, `Blocked` 중 하나로 보고하고 빠진 고정 계약을 수량과 함께 명시한다.
- 사용자가 실행하고 플레이하는 방법과 시작부터 엔딩까지의 흐름을 요약한다.
- 구현 계획이 선택한 주요 책임 경계와 저장 형식을 설명한다.
- T1부터 T6, R1부터 R23, AC1부터 AC31, V1부터 V4의 상태를 보고한다.
- 구현 단계에서 바인딩한 정확한 검증 명령과 각 명령이 증명한 pass intent를 보고한다.
- 정적 검사, 규칙 회귀, AC별 판정, 실제 브라우저, 스크린샷의 증거와 등록된 아티팩트를 보고한다.
- 추가한 테스트마다 막는 현실적 회귀와 유지비 정당성을 설명한다.
- 승인된 의미 계약과 다른 편차, 축소, blocked 항목을 숨기지 않는다.
- 사람에게 남은 판단은 HV1만 보고한다.
- 딜리버리는 `local`이며 커밋, 푸시, PR이 없음을 보고한다.
