# quick 증거 레인 설계 (핸드오프)

다른 세션에서 quick 스킬을 검토하다 나온 보강 설계다.
quick 본체 작업을 소유한 세션이 읽고 반영 여부를 결정하면 되고, 흡수한 뒤 이 파일은 삭제해도 된다.

## 문제

quick의 판사는 diff만 본다.
런타임 증거(스크린샷, DB 상태, API 응답)를 보는 레인이 없어서, 그런 증거가 필요한 AC는 현재 구조에서 판정 주체가 존재하지 않는다.
PRD 파이프라인에서는 독립 fidelity 리뷰가 이 레인을 담당하지만, quick에 리뷰어를 추가하면 LLM 호출이 1회에서 2회가 되고 quick의 존재 이유(최소 세리모니, 최소 대기)가 무너진다.

## 설계 원칙

- LLM 호출은 여전히 1회. 새 리뷰어, 새 단계를 만들지 않는다.
- 증거는 판사가 가지러 다니는 것이 아니라 하네스가 밀어넣는 재료다. 판사는 tool-less 단일 응답을 유지한다.
- 재현 가능한 증거는 하네스가 자기 시계로 직접 생성한다. finalize 재검증과 같은 원칙(실행 타이밍 주권은 하네스 소유)이다.
- 모든 증거는 해시로 PASS 핀에 들어간다. 통과 후 증거를 바꾸면 contract 해시, tree fingerprint와 마찬가지로 게이트가 다시 열린다.

## 증거 4계층

증거의 종류별로 이미 있는 장치에 얹는다. 위 계층으로 갈수록 신뢰도가 높으므로, 아래 계층으로 내려가는 것은 위 계층이 불가능할 때만 허용하는 것이 규칙이다.

### 1. 명령으로 재현 가능한 증거 -> mechanical 단계

"API가 200을 반환한다" 같은 AC는 그 curl/스크립트를 mechanical 명령으로 선언한다.
하네스가 직접 실행하므로 LLM 비용 0, 제출 편향 불가.
현재 `agents/config.json`의 `verify.commands`가 이미 이 역할을 하므로, contract별로 명령을 추가 선언할 수 있게 여는 것이 구현의 전부다.

### 2. 텍스트 증거 (로그, DB 덤프, API 응답) -> 판사 프롬프트 인라인

contract의 AC에 `evidence: <경로>` 선언을 허용한다.
verify가 (a) 파일 존재를 mechanical 단계에서 확인하고, (b) 내용을 diff와 함께 판사 프롬프트에 넣고, (c) 파일 해시를 PASS 핀에 포함한다.
프롬프트 폭주를 막기 위해 용량 상한(예: 파일당 수십 KB, 초과 시 BLOCK finding으로 "명령 재현으로 전환하라" 안내)을 둔다.

### 3. 이미지 증거 (스크린샷) -> 하네스 캡처 + 판사 첨부

이미지를 보는 것과 툴을 주는 것은 별개다.
판사를 tool-less로 만든 이유는 에이전시(툴 + 다턴 방황, 24턴/260초 기록)였고, 프롬프트에 첨부된 이미지는 텍스트와 같은 입력 재료라서 이 구조를 깨지 않는다.

핵심은 첨부 방식보다 출처다.
에이전트가 찍어온 스크린샷은 오래됐거나 조작됐을 수 있고 판사는 이를 구분하지 못한다.
따라서 contract는 이미지 파일이 아니라 캡처 명령(playwright 스크립트 등)을 선언한다:

1. contract가 AC에 `capture: <명령>`을 선언한다.
2. mechanical 단계가 하네스 시계로 그 명령을 실행해 신선한 캡처를 생성한다.
3. 하네스가 그 캡처를 판사에게 첨부한다.
4. 캡처 해시가 PASS 핀에 들어간다.

백엔드별 첨부 구현:

- codex 백엔드: `codex exec --image <path>`가 이미 있다.
- claude 백엔드: `claude -p`의 이미지 첨부 지원 여부를 먼저 확인하고, 안 되면 하네스가 Anthropic API를 직접 호출해 image content block으로 넣는다. 판사 백엔드 추상화(`cli/src/judge/backends.ts`)에 attachment 지원 여부를 capability로 추가한다.
- 최후 fallback으로만 "등록된 artifact 경로 한정 Read 툴 + 턴 제한"을 고려한다. 방황 리스크를 다시 여는 것이므로 첨부가 불가능한 백엔드에서만.

### 4. 재현 불가능한 증거 -> requiresHuman

캡처 명령으로 재현할 수 없는 증거(사용자 제공 디자인 시안과의 비교, 실기기 동작 등)가 달린 AC는 판사가 판정하지 않고 requiresHuman finding으로 떨어뜨려 경로와 함께 사용자에게 핸드오프한다.
Stop hook이 이미 허용하는 정지 사유이므로 추가 장치가 필요 없다.
사람이 증거 레인이 되는 것이고, quick의 규모에서 이것이 정직한 답이다.

## 판정 범위의 한계 (명시할 것)

판사의 시각 판정은 명제 확인("다크모드 토글이 렌더된다")에는 충분하지만 시각 품질(간격, 위계, taste)은 판정 대상이 아니다.
SKILL.md에 "taste 판단이 필요한 AC는 쓰지 말고 최종 리포트의 human review 항목으로 넘겨라"를 명시한다.
implement의 fidelity 리뷰가 "human taste judgment는 분리 명시"로 처리하는 것과 같은 선이다.

## 구현 접점

- contract 파서: AC 행의 `evidence:` / `capture:` 필드 파싱.
- `cli/src/gates/commands.ts` verify 흐름: mechanical 단계에 증거 존재 확인 + 캡처 명령 실행 추가, 증거 해시를 PASS 핀에 합류.
- `cli/src/judge/backends.ts`: attachment capability 추가, codex `--image` 경로와 claude 경로(CLI 첨부 또는 API 직접 호출) 분기.
- 프롬프트 렌더러: 텍스트 증거 인라인 섹션 추가(용량 상한 포함).
- Stop hook: 변경 없음. 기존 requiresHuman 허용 경로를 그대로 쓴다.

## 잔여 리스크 (의식적 수용)

- 계층 2의 텍스트 증거는 에이전트가 파일 자체를 조작할 수 있다. "계층 1로 갈 수 있는 것은 전부 계층 1로"가 이 리스크를 좁히는 규칙이고, 판사가 같은 콜에서 증거의 의미(diff와의 정합)를 함께 보는 것이 나머지를 막는다.
- 캡처 명령 자체가 잘못 짜였으면(엉뚱한 화면을 찍음) 판사는 찍힌 것만 본다. 이것은 PRD 파이프라인의 verification 명령 오염과 같은 클래스이므로, prelint의 Method 셀 규칙과 같은 정적 검사를 capture 명령에도 적용할 수 있다(후속 과제).
