# 전체 요구 검토 방식의 실제 실행 검증

같은 요구사항으로 제품 코드가 없는 출발점에서 구현부터 receipt까지 실행한 후속 측정은 [구·신 버전 전체 실행 비교](workflow-simplification-pilot/full-implementation-comparison/README.md)에 있다.
아래의 21.353→26.665초는 이미 완성된 코드의 검증 경로를 비교한 과거 수치이며 구현 시간을 포함하지 않는다.

## 결과 범위

이 문서는 workflow simplification 후보의 실제 실행과 전환 결과를 기록한다.
2026-09-08의 제한된 실험을 마친 시점의 기록이다.
하네스 소스는 검사를 마친 후보 상태이고, 두 제품 파일럿 가운데 하나는 완료됐으며 하나는 추가 승인된 여섯 번째 검증도 FAIL로 보존됐다.
후보와 수정 커밋은 main에 반영했고 양쪽 전역 skill과 CLI 설치를 마쳤다.
설치본 smoke는 세 번째 실제 검증도 FAIL로 끝나 정한 실험 범위에서 중단했고, 새 receipt 발급까지는 확인하지 못했다.
행별 PASS 기록과 별도 증거 제출 절차를 없애고, 전체 요구사항과 실제 결과를 함께 검토하는 변경이다.

| 판단할 항목 | 현재 결과 |
| --- | --- |
| 절차가 가벼워졌는가 | 동일한 작은 정상 사례에서 CLI 명령 9→4회, 모델 호출 8→1회 |
| 실제 시간이 줄었는가 | 이번 비교에서는 줄지 않음: 정상 21.353→26.665초 |
| 결함을 잡는가 | 같은 의미상 누락을 양쪽 리뷰가 탐지; 제품 결함 세 변형은 suite가 차단 |
| 정상 완료를 만들 수 있는가 | 한 제품 파일럿과 신형 비교 사례는 완료·receipt 확인 |
| 전체 요청을 마쳤는가 | 미완료: 다른 제품의 F11과 설치 smoke의 요구 해석 문제가 남음 |

관리 절차 축소는 확인했고, 리뷰가 요구 범위를 넓히거나 이전 지적을 끌고 가는 비용은 해결됐다고 볼 수 없다.

## 확인된 소스

후보 커밋은 `c96a6621d655d984df4322fb12aa0236a6856f93`, CLI 계약은 `0.9.0`이다.
이전 지원 소스와 사용자 수정은 보존한 독립 worktree에서 구현했다.
최종 동일 소스에서 clean build, root 98/98, unit 440/440, E2E 119/119, diff check가 통과했다.
검사 전후 소스 해시는 `442345e3ebe1454101185485c8c14c3acd96dbdc076882d1ce66532add29771a`로 같았다.

| 책임 | 이전 | 변경 후 |
| --- | --- | --- |
| 요구 보존 | 행별 구현·검증 상태 | 전체 PRD와 정적 요구 참조 |
| 구현 순서 | 행 생명주기와 검증 lane에 맞춤 | 구현자가 사용자 흐름에 맞게 결정 |
| 실제 확인 | 행별 check·QA brief·trail·자료 연결 | 필요한 흐름을 확인하고 실행 단위 자료 등록 |
| 독립 검토 | 행별 판정과 별도 fidelity·design 단계 | 필수 suite 다음 전체 계약 종합 검토 |
| 결과 기록 | 요구별 PASS·score | 구체적인 결함·권고·사람 확인과 해결 이력 |
| 완료 | 여러 행의 완료 집계 | 현재 입력의 suite·독립 검토·권한을 확인한 receipt |

필수 suite 실제 실행, 현재 소스·PRD·자료의 무결성, 실행 전체 소유권, 독립 판정, 제한된 수정 반복, 사람의 권한은 유지한다.
요구사항이 34개라는 이유로 34번 CLI 명령이나 34개 증거 파일을 요구하지 않는다.
모든 요구가 검토 입력에 있다는 것은 모델의 누락 가능성이 사라진다는 뜻이 아니다.

## 동일 입력의 두 구현

제품은 로컬 링크 관리 화면 Link Pocket이다.
생성·수정·검색·태그·저장 복원·삭제 복구와 실제 저장 실패 처리를 포함한다.
공통 starter는 `0f2e1b20d644be9c897904c6900c6b9da16f7808`이며 제품 기능이 없는 동일 출발점이다.
PRD 작성자는 Codex Sol medium이고, 구현은 Codex Sol medium과 Claude Code Opus 5의 독립 native session에서 수행한다.
이는 런타임별 동작 확인을 위한 파일럿이며 모델 성능 비교 실험은 아니다.

PRD는 Behaviors 34개, Decisions 14개이며 해시는 `916b23f4663f087c42685bc4715301dad4fa97b2049d64ac4e0f2180a7eb3cf4`다.
작성 단계 지시가 제품 제한과 새 승인 조건에 섞인 부분을 한 번 교정했고, 제품 요구 34개는 유지했다.
`ready`와 `human_approval: pending`을 정직하게 보존하고 기존 사용자 원문 위임을 conversational approval로 사용했다.
가상의 인터뷰나 사용자 응답을 만들지 않았고 conversation-only PRD의 spec gate는 미실행이다.

두 구현은 제품 코드를 공유하지 않으며, 같은 PRD·starter·필수 명령을 사용한다.
포트만 충돌하지 않도록 각각 분리했다.
각 프로젝트의 실제 skill 사본과 후보 CLI를 고정하여 전역 구형 설치와 섞이지 않게 했다.
Claude는 project/local 설정만 읽는 native print session을 사용하므로 전역 설정을 사용하는 통상 실행의 확인은 설치 후 별도로 기록한다.

## 실행 결과와 비용

Claude 제품은 수정 CLI에서 최종 종합 리뷰 PASS, `complete` 상태, 전달 가능한 v5 receipt와 로컬 커밋 `6a258f845c58c1a7ba93ac7bb27a09eb16667cfc`까지 완료했다.
마지막 시도는 `f20385c1-a8a1-4c23-ac45-5b1a2386359f`이며 필수 명령이 실제 42개 브라우저 테스트를 통과했다.
같은 시도의 suite는 23.017초, 종합 리뷰는 83.109초, 전체 verify는 107.021초였다.

Codex 제품은 기존 후보에서 네 번, 수정 후보에서 한 번의 실제 FAIL을 기록해 최초 5회 한도에 도달했다.
다섯 번째 `007f434d-0af3-4455-99e6-8d5aaca1bd05`가 남긴 초기 로딩 안내와 Retry 후 포커스 유실을 수정한 뒤, 사용자가 추가 검증 1회를 승인했다.
여섯 번째 `1aceb650-f007-47c2-bb58-6213ef8da4f4`는 suite 9.215초 PASS, 종합 리뷰 510.281초 FAIL이었다.
앞선 두 문제는 해결됐지만 삭제·복구·초기화 전환의 포커스 유실을 F11로 남겼다.
추가 승인 1회는 사용했으며 그 이후의 검증, finalize, ship은 실행하지 않았다.
제품은 일반 보존 커밋 `c3dd486948fc4a2655eacfcc212c43ec57c90683`으로 고정했고 원래 state는 active/FAIL, receipt는 없는 상태다.
이 커밋은 완료나 전달을 뜻하지 않는다.
예산 초기화, 새 실행으로 우회, 가짜 승인, 실패의 PASS 치환은 하지 않았다.

현재 측정 스냅샷은 [실행별 JSON](workflow-simplification-pilot/metrics.json)에 있다.
기존 7일 감사와는 동일 조건의 속도 비교로 해석하지 않는다.

기존 7일 감사의 실질 실행 16개에는 요구 292개, 행별 check 1,307회, 통합 verify 65회가 있었다.
각 실행 안에서 중복 시간을 제거한 verify 구간의 합은 351.3분이었다.
행별 check의 자원 시간 106.2분은 verify 시간과 겹치므로 두 숫자를 더하지 않는다.
현재 파일럿 두 실행에는 행별 check가 없고, 필수 suite 실행과 전체 계약 리뷰만 기록된다.

최초 후보의 실제 backend smoke에서 Codex는 심은 누락과 이미지 확인을 통과했지만, 일부 사례에서 불필요한 요구별 실행 증거를 추가 요구했다.
Claude smoke는 잘못된 요구 참조 출력으로 실패했다.
제품 파일럿에서는 기존 conversational approval이 판정 입력에 빠져 불필요한 human-confirmation 출력 오류도 발생했다.
별도 correction 작업트리에서 동일 참조·human-source context와 명확한 증거 충분성 기준으로 수정했다.
수정 커밋은 `f6963672454207cbce08908cc33eaf6e74d866c7`이며 부모는 최초 후보 `c96a662`다.
수정 커밋의 tree `453c9e86609e9e1a4d9f05209b81e4325de50bcd`에서 clean build/noEmit, root 98/98, unit 447/447, E2E 120/120을 통과했다.
두 실제 판정 backend 모두 정상·중간 누락·마지막 누락·미연결·저장 실패·승인된 가정 여섯 source 사례의 정확한 blocking 기대값을 충족했고, 무관한 blocking 요구나 새 사람 승인 조건을 만들지 않았다.
Codex의 실제 이미지 자료 검토도 통과했다.
최종 smoke의 실제 호출은 Codex 8회, Claude 6회이며 fallback은 없었다.
Codex 1회 재시도는 읽기 전용 명령 검사에서 `printf`가 거부된 경우이고, 참조 schema 오류는 없었다.
이전 실패와 별도 수정 검사의 비용을 정상 최종 검사에서 지우지 않는다.
그 과정에서 정상 smoke fixture가 `Error` 외 throw 값을 처리하지 못하는 실제 결함도 발견해 fixture만 수정했으며, 심어 둔 저장 실패 변형은 유지했다.

Codex 제품의 첫 종합 리뷰는 실제 포커스 처리와 긴 선택 태그의 모바일 넘침, 필요한 runner 설정 접근 부재를 찾았다.
후속 판정은 이미 해결된 문제를 닫고, 남은 오류 포커스와 empty 상태의 0 count를 구체적으로 남겼다.
Claude 제품의 독립 브라우저 QA는 핵심 네 흐름과 실제 저장 실패, 360px 조작을 통과했다.
그 시점에는 human-source 출력 계약 오류 때문에 최종 receipt는 아직 없었다.

Codex의 네 차례 기존 후보 리뷰는 약 2.5~5분씩 걸렸고, 후속 수정 과정에서 loading 상태의 실제 paint, 지속되는 live region, 다시 읽기 안내와 undo 저장 실패 표시 같은 추가 문제도 발견했다.
이는 행별 절차 삭제가 리뷰 반복 비용까지 자동으로 없애지는 않는다는 관찰이다.
다섯 번째 이후의 허용된 검증과 최종 전달은 수정 CLI를 사용하며 이전 결과는 기존 후보의 결과로 보존한다.

Claude native print 실행이 background verify를 남기고 종료되는 문제를 한 번 복구했고, 동일 오류의 무변경 반복을 막기 위해 coordinator가 한 번 중단했다.
같은 native session과 원래 run을 유지해 interactive 실행으로 전환했으며, 모든 실패와 중단 기록을 보존한다.
이는 현재 파일럿의 실행 비용과 제약으로 기록한다.
실행 시간은 구현, 집중 검사, 브라우저 관찰, CLI verify의 필수 suite와 judge, 최종 전달로 구분한다.
동시에 진행한 작업 시간을 단순 합산해 실제 경과 시간으로 쓰지 않는다.
정상 두 구현과 고의 결함 세 변형은 각각 별도 결과로 기록한다.

## 판정의 수렴성과 환경 복구

F11은 한 번의 제한된 읽기 전용 비교로 해석 경계를 확인했다.
B30/D11은 피드백 안내가 현재 포커스를 빼앗지 않아야 한다고 정하지만, 제거된 성공 동작 버튼마다 다음 포커스 대상을 지정하지는 않는다.
이미 완료된 다른 구현에도 삭제·복구·초기화 성공 때 버튼이 사라지는 유사 구조가 있어, 모든 성공 전환을 일괄 결함으로 보는 해석은 명시된 요구보다 넓다.
다만 실패한 초기화에서 유지 가능한 버튼을 화면 재생성으로 잃는 경로는 실제 소스상 근거가 있어 F11 전체를 무효화하거나 FAIL을 PASS로 바꿀 수 없다.
이 비교는 소스 해석이며 새로운 브라우저 관찰이나 독립 판정 PASS가 아니다.
행별 절차를 없앤 뒤에도 새로운 리뷰가 매번 판단 범위를 넓히는 비용이 남는다는 사례로 기록한다.

프로젝트 내부로 일반 파일을 복사한 skill staging은 제품의 `type: module`을 상속해 CommonJS `prd_ship.js`가 실행되지 않는 환경 결함이 있었다.
Claude 파일럿은 동일 바이트 script의 CommonJS scratch 실행으로 같은 검증·freshness·허용 파일 staging을 거쳐 로컬 전달을 끝냈다.
코디네이터가 원래 staged 경로의 실패를 재현한 뒤, 두 runtime의 staging root에 CommonJS package scope만 추가했다.
Script 바이트와 제품 소스는 유지했고 원래 documented 경로의 `ship status`도 같은 receipt에서 성공했다.
실제 설치기는 source symlink로 원래 package scope를 보존하므로 이 관찰만으로 운영 script를 개명하거나 새 설치 모드를 추가하지 않았다.

독립 브라우저 평가의 원본은 [A 보고서](workflow-simplification-pilot/qa/a/report.md)와 [B 보고서](workflow-simplification-pilot/qa/b/report.md)에 있다.
A는 확인 중 소스가 바뀌어 관찰한 소스의 주요 흐름 PASS와 최종 트리 INCONCLUSIVE를 분리했고, 표준 Browser pane 연결 실패 뒤 standalone Chromux 관찰을 했다는 제한을 남겼다.
B의 독립 관찰도 후속 두 소스 수정 이전 자료이며, 그 수정은 현재 source의 실제 42개 테스트와 종합 리뷰로 확인했다.
과거 캡처를 최신 전체 제품의 독립 PASS로 재명명하지 않는다.

심어 둔 제품 결함 세 변형은 모두 필수 suite에서 FAIL로 차단됐고, 모델 판정과 finalize는 실행되지 않았다.
양쪽 원본의 결과를 보존한 다음, 완료된 Claude 제품에서 저장 복원 연결 제거·검색 결과 연결 제거·저장 실패 무시를 각각 하나씩 심어 새 실행에서 검증한다.
처음의 양쪽 완료 선행 조건은 실험 준비 조건만 수정했다.
Codex 원본의 FAIL과 receipt 부재는 유지하고, 완료된 제품만 변형의 출발점으로 사용한다.
세 파생 실행은 필수 테스트를 유지하고 포트만 미리 분리해 서로 독립적으로 실행하도록 준비했다.
저장 복원 누락은 로드한 행이 보이지 않아 브라우저 동작이 반복해서 실패했고 전체 suite가 300초 제한에서 종료됐다.
검색 연결 오류는 44.165초, 저장 실패 무시는 48.447초에 필수 suite가 실패했다.
세 사례 모두 judge 호출은 0회이며 잘못된 완료 receipt는 발급되지 않았다.
원본·변경 diff·실제 suite 출력과 판정은 [변형별 결과](workflow-simplification-pilot/mutations/summary.json)에 연결한다.
이 수치는 suite 탐지이며 judge 탐지로 세지 않는다.

main은 `e453351`까지 fast-forward로 통합했다.
최종 검사 소스 `f696367` 이후 변경은 감사 자료와 역할 검사 안내 두 문장뿐이며 운영 코드·테스트·설치기는 같다.
구형 generated dist를 보존 경로로 옮긴 뒤 정상 installer로 새 dist와 전역 CLI `0.9.0`, 양쪽 skill 10개씩을 설치했다.
Codex의 새 prompt 입력과 Claude의 새 native `/skills` 화면에서 10개 모두 발견했고, Codex의 SKILL.md는 일반 파일이다.
현재 main에서 root 98개 검사를 통과했다.
설치된 CLI의 실제 실행은 확인했지만, 새 smoke 완료는 아래와 같이 미완료다.
살아 있는 구형 schema 실행 의존성은 최신 관찰에서 발견되지 않았으며, 소유자가 불일치하는 역사적 기록은 수정·종료하지 않았다.

## 설치본에서 추가로 발견한 한계

새 native session에서 실제 설치 skill을 불러, 아직 제품 코드가 없는 작은 라이브러리를 시작·구현·검증했다.
최초 native 실행은 새 폴더 신뢰 화면에서 종료돼, 같은 CLI 생성 pane에서 실제 화면 확인 후 새 native process로 복구했다.
실제 발견된 skill 10개, CLI 계약, 소유권, 시작 순서와 비어 있지 않은 구현 diff를 확인했다.
가짜 판정이나 진단 override 없이 실제 backend로 세 번 검증했다.

| 설치 smoke 시도 | 실제 suite | 종합 리뷰 | 결과 |
| --- | ---: | ---: | --- |
| 1 | 0.502초 PASS | 40.049초 | 변경하지 않은 테스트·관찰 호출자 소스에 접근할 수 없어 FAIL |
| 2 | 0.487초 PASS | 55.926초 | 호출자 자료를 공통 등록해 앞선 문제 해결; 완료 후 receipt 소비 증명을 완료 전 조건으로 요구해 FAIL |
| 3 | 0.496초 PASS | 24.798초 | 같은 실행의 Goal 범위를 고쳤지만 F2를 계속 OPEN으로 남겨 FAIL |

두 번째 문제의 시작은 coordinator가 작성한 PRD Goal에 제품 동작과 설치 확인 절차를 섞은 것이었다.
완료 기록은 finalize 후 생기므로 그 소비 결과를 finalize 전 필수 검토에서 요구하면 순서가 순환한다.
원래 사용자 위임 범위 안에서 Goal과 review_rationale 두 줄만 수정해 같은 실행에서 amend했고, 제품 행동·결정·suite·소스·설정은 보존했다.
CLI도 요구 추가·삭제·변경 없음과 suite 변경 없음을 기록했고, 이전 PRD는 폐기하지 않고 보관했다.

세 번째 리뷰는 수정된 PRD를 받았고 제품의 정규화·실패 동작은 충족한다고 썼으나, 이전 F2의 설치 경계 증거를 계속 요구했다.
한 번의 독립된 읽기 전용 대조에서도 현재 Goal·Non-goals·Decisions·Behaviors·Technical structure·Risks에 receipt 소비를 요구하는 문장은 없었다.
특히 Non-goals는 delivery를 제외하며, Risks의 새 skill 발견 맥락만으로 receipt 소비를 필수 제품 조건으로 만들 수는 없다.
따라서 이 입력의 판정은 현재 계약에 없는 조건을 계속 요구한 구체적인 오판이다.
수정 전 지적에 고정돼 새 실행 증거만 해결 근거로 인정한 것이 가장 타당한 설명이지만, 한 호출의 관찰만으로 일반적인 발생률이나 결정적인 내부 원인을 확정하지 않는다.
현재 state는 active/FAIL, 3/5회 사용, grant 0회, receipt 없음이다.
실험에서 정한 중단 조건에 따라 네 번째 리뷰·추가 amendment·finalize·완료 후 doctor·새 receipt에 대한 두 소비자 확인은 실행하지 않았다.
예산 소진으로 중단된 제품 파일럿과 달리 이 smoke는 실험 범위 때문에 멈췄다.

별도 읽기 전용 확인에서 양쪽 설치 ship 도구는 이미 완료된 제품의 v5 receipt와 현재 소스 일치를 읽었다.
그 기록의 status는 complete, eligible과 deliveryFreshness는 true이며, 로컬 전달 기록이라 PR-mode 필드 modeOk는 false였다.
이 확인을 PR 전달이나 새 smoke의 완료 증명으로 바꾸어 쓰지 않는다.
양쪽 원본의 state·receipt 해시와 제품 커밋은 확인 전후 같았다.

실험 중 기존 기계의 Stop hook이 제품 파일을 자동 checkpoint 커밋한 환경 사건도 기록한다.
제품 바이트는 바뀌지 않았고, 이를 숨기기 위해 외부 hook을 끄거나 Git 이력을 재작성하지 않았다.
설치·발견·세 판정·amendment·원본 보존 근거는 [설치 기록](workflow-simplification-pilot/installation/summary.json)에 있다.

## 구버전과 같은 작은 기능 비교

동일 코드·요구 6개·필수 Node suite를 구형과 신형에서 각각 정상·누락 상태로 실제 실행했다.
정상 코드와 한 가지 의미상 누락 코드의 해시가 각 버전에서 같고, PRD는 동일 요구에 구형의 검사 열만 추가한 형태다.
예를 들어 항목이 하나일 때 `1 item`을 반환해야 하는데 `1 items`를 반환하도록 같은 누락을 심었다.
두 버전 모두 정상은 PASS와 receipt, 누락은 FAIL과 receipt 부재로 끝났다.
네 사례 모두 동일 suite를 한 번 실행해 통과했으므로 이 누락은 실제 모델 리뷰가 발견한 결과다.

| 측정 | 구버전 0.8 | 신버전 0.9 |
| --- | ---: | ---: |
| 정상 완료까지 CLI 명령 | 9회 | 4회 |
| 자료 등록 | 요구별 6회 | 공통 1회 |
| 실제 모델 호출 | 8회 | 1회 |
| 필수 suite 실행 | 1회 | 1회 |
| 정상 state 크기 | 29,101 bytes | 9,955 bytes |
| 정상 판정 입력 토큰 합계 | 180,946 | 24,975 |
| 정상 전체 경과 시간 | 21.353초 | 26.665초 |
| 누락 전체 경과 시간 | 20.531초 | 33.639초 |

구형의 여덟 호출은 요구별 여섯 판정, fidelity, design이었다.
상위 acceptance/fidelity 두 항목만 세면 실제 호출을 누락하므로 provider invocation 기록을 기준으로 셌다.
구형은 병렬 판정이라 호출 수 감소가 벽시계 시간 감소와 같지 않으며, 이번 신형 종합 리뷰의 경과 시간은 더 길었다.
입력 토큰은 캐시된 토큰을 포함한 합계이며 가격이나 실제 청구액으로 해석하지 않는다.
모든 비교가 다른 브라우저 결함 실험과 일부 겹쳤고, 동일 조건 반복 실험은 아니므로 일반적인 속도 개선율을 산출하지 않는다.
구형 빌드는 기존 DOM 타입 오류 때문에 소스 변경 없이 `--lib ES2022,DOM`으로 비교용 dist를 만들었다는 차이도 기록한다.
원본 수치와 입력은 [비교 기록](workflow-simplification-pilot/version-comparison/report.md)에 있다.
이 비교는 고정된 구현을 처리하는 하네스 절차의 재생이며, 두 버전으로 새로 구현하는 속도 비교가 아니다.

## 남는 한계

관리 절차·모델 호출·입력량은 줄었지만, 종합 리뷰의 지연과 판단 범위 확대를 해결했다고 주장하지 않는다.
한 제품의 두 구현과 세 결함 변형은 임의의 프로젝트에 대한 탐지율이나 무결함을 보장하지 않는다.
전체 계약 종합 검토가 놓친 결함, 불충분한 근거, 환경 실패는 해당 결과에 그대로 남긴다.
