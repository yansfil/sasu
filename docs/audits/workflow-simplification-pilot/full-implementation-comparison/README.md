# 같은 요구사항의 구·신 버전 전체 실행 비교

같은 요구사항 여섯 개를 구·신 버전의 PRD 형식으로 준비하고, 제품 코드가 없는 같은 출발점에서 각각 구현해 최종 PASS와 receipt까지 완료했다.
이제 구현 시작부터 완료까지의 시간과 병목을 실제 기록으로 비교할 수 있다.
다만 한 번씩 실행한 작은 사례이고 준비 오류와 환경 복구가 섞여 있어 일반적인 속도 개선율로 해석하지 않는다.

## 무엇을 같게 했는가

제품은 제목 정리, 빈 제목 거부, 완료 전환, 삭제, 방어적 복사, 단복수 요약을 제공하는 작은 작업 목록 라이브러리다.
[구형 PRD](old/case/prd.md)와 [신형 PRD](new/case/prd.md)의 여섯 Behavior 문장은 정확히 같다.
구형의 검사 방법 열과 각 버전이 요구하는 benchmark schema만 다르다.
화면, 저장소, 네트워크가 없는 작은 사례이므로 큰 UI 제품의 속도까지 대표하지는 않는다.

| 고정한 조건 | 값 |
| --- | --- |
| 제품 출발점 | commit `c8191eff3b08cd63a7c349c7eda964fcd6bac83d`, 제품 구현 파일 없음 |
| 기본 자료 | 같은 package, 테스트, judge 설정 바이트 |
| 구현자 | Codex `gpt-5.6-sol`, medium, 버전마다 새로운 native session |
| 판정자 | Codex `gpt-5.6-luna`, xhigh, fallback 없음 |
| 실행 순서 | 구형 완료 후 신형 시작, 구현 구간 겹침 없음 |
| 구형 하네스 | `488d3cc7d6e99742e7f68a1680fcb101710c8e20`, CLI 0.8.0 |
| 신형 하네스 | `a04ebf3edb7b01b2888e035bd4f92f8e118ca2b1`, CLI 0.9.0 |

각 실행이 고정한 local skill과 CLI를 실제로 읽고 사용한 것을 transcript에서 확인했다.
완성된 코드나 이전 실행의 정답은 구현자에게 주지 않았다.
두 구현은 독립적으로 만들어졌고 소스 바이트가 다르다.
구형은 기본 테스트를 그대로 유지했고, 신형은 기본 905바이트를 그대로 보존하며 빈 제목 추가와 단수 요약 테스트 두 개를 덧붙였다.
PRD와 case 파일이 형식상 다르므로 전체 source fingerprint와 문서 해시는 같지 않다.
제품 starter와 여섯 요구의 동일성을 기준으로 한 비교다.

## 실제로 얼마나 걸렸는가

첫 작업 지시가 native session에 들어간 시각부터 receipt의 완료 시각까지를 총시간으로 잡았다.
그 안에서 준비를 마치고 CLI 실행을 시작한 뒤의 시간도 별도로 계산했다.
나중에 수행한 독립 평가와 이 보고서 작성은 두 시간 모두에서 제외한다.

| 겹치지 않는 구간 | 구형 | 신형 |
| --- | ---: | ---: |
| 스킬 읽기·실행 준비 | 279.365초 | 72.011초 |
| CLI 시작 → 첫 검증 요청 | 125.532초 | 147.020초 |
| 실제 verify 구간의 합 | 25.965초 | 63.009초 |
| 실패한 verify 뒤 재시도까지 | 0초 | 9.605초 |
| 최종 PASS → receipt | 14.733초 | 61.346초 |
| **첫 지시 → receipt** | **445.595초, 약 7분 26초** | **352.992초, 약 5분 53초** |
| **CLI 시작 → receipt** | **166.230초, 약 2분 46초** | **280.981초, 약 4분 41초** |

밀리초 기록 반올림 때문에 신형 구간 합과 전체 시각 차이에 1밀리초 차이가 있다.
첫 검증 전 구간에는 구현, 집중 검사, 자료 작성, 명령 사이의 대기가 함께 들어간다.
이 구간 전체를 모델의 순수 코딩 시간이나 추론 시간으로 부르지 않는다.
관측되지 않은 활동을 추정해 채우지 않았다.

| verify 안에서 관측한 항목 | 구형 | 신형 |
| --- | ---: | ---: |
| verify 호출 | 1회 PASS | 1회 ERROR 뒤 1회 PASS |
| 필수 suite 실행 시간 합 | 0.547초 | 0.483초, 두 번 실행 |
| 실제 판정 모델 호출 | 8회 | 3회, 오류 두 번 포함 |
| 판정 구간의 경과 시간 합 | 25.305초 | 62.353초 |
| 마지막 성공한 verify | 25.965초 | 24.922초 |
| 검증 이후 제품 수정 | 없음 | 없음, 동일 입력으로 오류 복구 |

위 suite와 판정 시간은 verify 내부의 상세 항목이며 전체 시간에 다시 더하지 않는다.
구형은 요구별 판정 여섯 개와 fidelity·design을 병렬로 실행했다.
따라서 여덟 판정의 시간 합 172.397초가 실제 대기 25.305초를 뜻하지는 않는다.
신형은 종합 판정 하나로 끝나는 구조지만, 이번에는 오류 복구 때문에 실제 모델 호출이 세 번이었다.
신형에서 실패한 두 호출의 토큰 사용량은 없으므로 성공 호출의 토큰만으로 총비용 절감률을 계산하지 않는다.

## 어디서 시간이 들었는가

**구형의 총시간에는 준비 문제와 조정 대기가 크게 들어갔다.**
처음 PRD readiness는 통과했지만 benchmark 준비기가 공백 있는 topic을 거부했다.
아직 run이나 제품 코드는 없는 상태에서 양쪽 topic만 같은 유효 형식으로 고쳤다.
첫 실패부터 같은 세션의 준비 재시도까지 154.006초가 걸렸고 이 시간은 그대로 총시간에 포함했다.
신형은 이 공통 수정이 끝난 뒤 시작했다.
그러므로 총시간 7분 26초와 5분 53초의 차이를 신형의 성능 개선이라고 할 수 없다.
구형 세션에서는 같은 설명 문서를 다시 읽거나 테스트 결과를 자료로 저장하려고 같은 테스트를 다시 돌리는 작은 중복도 관측됐다.

**신형의 검증 지연은 제품 결함이 아니라 판정 실행 오류였다.**
첫 판정이 허용되지 않은 `package.json` 읽기 때문에 거부됐고, 내부 재시도는 최종 응답이 비어 ERROR로 끝났다.
그 verify는 38.087초를 썼다.
제품 코드와 입력을 바꾸지 않은 정상적인 오류 재시도에서 다음 판정은 PASS했다.
실패 이력과 실제 호출 수를 유지했고 예산 초기화나 fallback 전환은 없었다.

**신형의 완료 직전에는 디스크 오류가 있었다.**
최종 PASS 뒤 첫 finalize가 state 파일의 원자적 rename 중 `ENOSPC`로 실패했다.
세션은 디스크와 실패한 임시 파일을 확인했고, 거부된 `rm -f` 시도 뒤 그 임시 파일 두 개만 휴지통으로 옮겨 finalize를 다시 실행했다.
원래 state나 receipt를 수동으로 편집하지 않았다.
이 복구를 포함한 61.346초 전체를 정상적인 완료 처리 비용으로 해석하지 않는다.
관련 명령과 실제 결과는 [관측 발췌](analysis/new-observable-excerpts.json)에 원래 transcript 행 번호와 함께 보존했다.

## 완료 증거와 측정의 한계

구형은 [v4 receipt](old/run/receipt.json), 신형은 [v5 receipt](new/run/receipt.json)가 `complete`와 현재 입력의 PASS를 기록한다.
구형 제품 보존 커밋은 `f9ac3ea7cb5b74304119af7bd8e5717a487ca295`, 신형은 `23d515c1ea0e62d0c124c37dd112603f8cd70288`이다.
보존 커밋은 receipt 이후이므로 구현 시간에 넣지 않았다.
두 실행 모두 finalize 중 테스트나 판정 호출은 0회다.

정식 benchmark 보고서 발급은 양쪽 모두 실패했다.
준비기는 topic에서 `agents/runs/matched-task-list-library`를 예약했지만 구현 CLI는 PRD 폴더에서 `agents/runs/task-list-full`을 만들었다.
같은 준비 worktree에서 실행을 완료한 것은 확인되지만 예약된 run 경로와 receipt 경로의 연결이 맞지 않는다.
각 버전의 실제 reporter는 이 불일치를 거부했다.
[구형 오류](native-report-attempts/old.json)와 [신형 오류](native-report-attempts/new.json)를 보존했고 예약 기록이나 schema를 바꾸어 보고서를 만들지 않았다.
따라서 이것은 **receipt와 transcript에서 직접 추출한 전체 실행 실측**이며, 정식 native benchmark report의 성공이나 엄격한 cross-schema 비교 성공은 아니다.

두 완료 뒤에 서로의 결과를 보지 않은 새 Sol evaluator가 각 세션의 과정만 한 번씩 평가했다.
[구형 평가](analysis/qualitative-old.json)와 [신형 평가](analysis/qualitative-new.json)는 경로 연결 문제, 중복 준비, 오류 복구를 기록한다.
정성 점수를 버전 성능 점수로 사용하지 않는다.
평가 시간은 dispatch 확인부터 결과 수신까지 코디네이터가 측정한 별도 구간이며 실행 스케줄과 수집 지연도 포함한다.

## 다음 변경을 판단할 근거

요구별 판정과 자료 등록을 줄인 구조는 확인했지만, 한 번 성공한 검증 자체의 대기는 양쪽 모두 약 25초였다.
구형 판정이 이미 병렬이기 때문에 호출 수를 줄이는 것만으로 완료 시간이 같은 비율로 줄지는 않는다.
이번에는 모델 판정의 읽기·응답 오류, 준비기와 구현 CLI의 경로 불일치, 반복된 설명 읽기가 실제 개선 대상으로 드러났다.
디스크 오류는 별도의 실행 환경 문제로 다뤄야 한다.
저장소 원칙 2와 9에 따라 검증 비용을 구현 구간과 분리해 측정했고, 원칙 10에 따라 실패와 완료 기록을 각각 보존했다.

더 안정적인 속도 비교에는 위 준비 결함과 환경 문제를 정리한 다음 동일 조건의 반복 실행이 필요하다.
이번 실패 시간을 임의로 빼서 가상의 정상 완료 시간을 만들거나, 작은 라이브러리 한 쌍으로 큰 서비스의 속도 개선을 주장하지 않는다.

정확한 시각·호출·소스 정보는 [process-metrics.json](analysis/process-metrics.json), 추출 방법은 [분석 도구 안내](analysis/README.md), 복사한 원본의 해시는 [evidence-manifest.json](evidence-manifest.json)에 있다.
